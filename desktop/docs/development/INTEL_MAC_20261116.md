# Intel Mac 桌面接入与构建记录（2026-11-16）

## 当前边界

本轮把 Intel 用户的本机模型接入、应用配置及目标资源获取路径接到了实际代码。**本轮没有生成或发布经过 Intel 真机验收的 APP、DMG 或依赖锁。** 本机推理走 OpenAI 兼容 HTTP 端点，CPU / GPU 的选择、GGUF 权重加载及内存管理由推理服务负责。MLX 权重与 Apple Silicon oMLX 资源不能直接当作 Intel 资源使用。

桌面最低版本继续为 **macOS 15.0**，没有降低 `tauri.conf.json` 中的系统要求。已有 Liquid Glass 降级和部分 Swift availability 判断不足以证明全部原生界面与观察能力可运行于更老系统。Intel macOS 14 及以下、Linux 原生桌面、Intel 原生音轨采集与睡眠唤醒均未通过本轮验收。

## 已接通的用户流程

1. Intel 首次设置的“准备 Agent”页面直接显示本机端点表单；模型库也默认展开这一表单。
2. 启动 llama.cpp 等服务后填写环回地址，点击“检查连接并读取模型列表”。Suite 只读取 `/v1/models`，不提交推理请求；模型 ID 可以选择，也可以手工填写。
3. 手工填入服务实际加载时的上下文上限。界面不从模型名称、文件大小或模型列表推断窗口，也不以一个默认 32K 窗口代替实测配置。
4. 明确选择是否让 Companion 使用这一端点、Companion 电源策略，以及是否请求后端关闭模型思考输出。电源策略不会修改系统电源设置；关闭思考只是后端选项，请另行检查实际输出。
5. 保存为新路由，保留原路由、Session 和收据。保存操作不会自动重启服务。活动任务结束后，点击“确认重启服务并应用配置”；Suite 复用已有停止与恢复流程，活动任务及未解决的批准会阻止重启。
6. 关闭再打开设置后，未应用的配置仍提供重启入口。新增本机路由后，协作主模型与子模型列表立即刷新。

Intel 模型库显示已配置的本机路由和连接状态，隐藏 oMLX 专用的搜索、下载、导入和加载入口。服务可连接、模型 ID 已注册、真实任务能完成是不同检查；这一界面不把连接成功显示为模型质量合格。

## 为什么需要独立的 Intel 依赖材料

之前 `wheel_supports()` 只查看 wheel 文件名末尾的架构，因此可能把 CPython 3.13、free-threaded 3.14、PyPy，或要求 macOS 16 的 x86_64 wheel 当作当前运行时材料。本轮改用 PyPA 的 wheel tag 解析，目标明确为标准 **CPython 3.14、macOS 15、指定架构**；保留兼容的较旧 `abi3` 和 universal2 wheel。

对现有 35 项固定依赖逐项查询官方 PyPI 元数据后，33 项具有兼容 Intel wheel。另两项需要从已固定的官方源码构建：

| 依赖 | 固定源码 | SHA-256 | 限制 |
| --- | --- | --- | --- |
| watchdog 6.0.0 | `watchdog-6.0.0.tar.gz` | `9ddf7c82fda3ae8e24decda1338ede66e1c99883db93711d8fb941eaa2d8c282` | 官方没有标准 CPython 3.14 macOS wheel |
| cryptography 50.0.2 | `cryptography-50.0.2.tar.gz` | `7b46165bb56eb4704e2eaaf86f3c940d19154535d9b0ca7d6d590b04060e00d5` | 此版本官方 macOS wheel 只有 arm64 |

本轮已实际获取并再次校验全部 35 份来源材料，共 11,831,279 字节：33 个 wheel 的分发元数据、Python 版本和目标 ABI / 平台均通过生成器检查，两个源码包待 Mac 编译。结果为 `NEEDS_NATIVE_SOURCE_BUILDS`，没有创建完整 Intel 依赖锁。公开材料见[逐文件来源与哈希](../evidence/intel-portability-20261116/dependency-acquisition.json)和[实际检查结果](../evidence/intel-portability-20261116/dependency-checks.json)。首次获取因固定 cryptography 缺失 Intel wheel 停止的日志仍保留；补齐源码路径后才完成获取。

原有 `runtime-dependencies.json` 保留其 Apple Silicon 基线。本轮不手填或虚构 Intel 二进制哈希。下载器校验官方文件哈希、wheel tag 和 `Requires-Python`；本地构建结果另行记录源码、产物哈希与工具链。没有完整 wheel 集合时不会生成 Intel 锁。

`build-watchdog-wheel.py` 保留原有 universal2 的严格可复现哈希检查，新增显式 `--arch x86_64` 原生构建并生成 `watchdog-build.json`。Intel 产物不冒用旧 universal2 哈希。

`build-cryptography-wheel.py` 只接受固定源码和原生 Intel Python 3.14.6，沿用源码的 `Cargo.lock` / `maturin locked=true`，用一个 Cargo worker 静态链接调用者指定的 OpenSSL。构建前检查静态库架构，构建后用 `lipo` / `otool` 检查扩展架构及外部动态依赖；OpenSSL 许可证加入生成的 wheel 并重建 `RECORD`。记录包含 OpenSSL 版本、静态库和许可证哈希、Rust、Clang、SDK 和 Python 构建工具版本。**记录构建输入不等同于已证明跨机器可复现或完成运行验收。**

## 在 Intel Mac 上准备资源

下面从仓库根目录执行。使用新的源码工作树与新的构建目录，保留已有 APP、资源目录、模型、日志和服务。不要把测试 APP 安装到日常身份。

### 1. 准备工具

需要 macOS 15+、原生 x86_64 CPython **3.14.6** framework、Xcode Command Line Tools、Rust（cryptography 此版本源码要求至少 1.83）、Node/npm，以及适合 Intel 的 OpenSSL 静态库和对应许可证。使用标准 Python，不使用 free-threaded Python。

```sh
uname -m
python3.14 -c 'import platform,sys; print(platform.machine(),sys.version,sys.base_prefix)'
LP_INTEL_BUILD="$HOME/LocalPilotIntelBuilds/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$LP_INTEL_BUILD"
python3.14 -m venv "$LP_INTEL_BUILD/venv"
. "$LP_INTEL_BUILD/venv/bin/activate"
python -m pip install 'setuptools==84.2.0' 'wheel==0.48.0' 'packaging==26.3' \
  'maturin==1.14.1' 'cffi==2.1.1' 'pycparser==3.12' build
```

cryptography 官方文档提供通过 Homebrew 或 MacPorts 获取 OpenSSL 与 Rust 的方式。选择已审核的 Intel OpenSSL 安装，将 `LP_INTEL_OPENSSL` 设为包含 `lib/libssl.a`、`lib/libcrypto.a`、头文件及 `bin/openssl` 的前缀；`LP_INTEL_OPENSSL_LICENSE` 必须指向同一版本的真实许可证文件。脚本会记录这些输入，不能用任意许可证文本代替。不要把 Apple Silicon Homebrew 库作为 Intel 链接输入。

### 2. 获取并生成目标依赖锁

```sh
python desktop/scripts/lock-runtime-dependencies.py \
  --arch x86_64 --download \
  --wheels "$LP_INTEL_BUILD/dependencies" \
  --out "$LP_INTEL_BUILD/runtime-dependencies-x86_64.json" \
  --openssl-dir "$LP_INTEL_OPENSSL" \
  --openssl-license "$LP_INTEL_OPENSSL_LICENSE"
```

在 Linux 上也可以执行同一脚本的下载部分，不传两个 OpenSSL 参数。结果应为 `NEEDS_NATIVE_SOURCE_BUILDS`，列出 `cryptography`、`watchdog`，`lock_created` 为 `false`；这只说明来源材料已经获取，不能继续打包为 Intel APP。将材料带到 Intel Mac 并重新执行原命令时，已下载文件会再次核验哈希，随后才运行原生源码构建。已存在的目标锁、wheel 或构建记录不会被覆盖。

遇到哈希不匹配、缺失同版本 wheel 或编译失败时，保留材料和失败日志。不要手改锁中的架构或版本来跳过检查。

### 3. 构建独立组件与桌面

四个组件必须来自同一待验收工作树。此步骤只生成 wheel，不能用历史安装中的组件代替源码。

```sh
python -m pip wheel --no-deps --no-build-isolation --wheel-dir "$LP_INTEL_BUILD/components" .
python -m pip wheel --no-deps --no-build-isolation --wheel-dir "$LP_INTEL_BUILD/components" ./companion
python -m pip wheel --no-deps --no-build-isolation --wheel-dir "$LP_INTEL_BUILD/components" ./suite
python scripts/build_channels_wheel.py --out "$LP_INTEL_BUILD/components" --no-isolation
python desktop/scripts/prepare-bundled-backends.py \
  --arch x86_64 --wheels "$LP_INTEL_BUILD/components" \
  --dependencies "$LP_INTEL_BUILD/dependencies" \
  --dependency-lock "$LP_INTEL_BUILD/runtime-dependencies-x86_64.json"
python desktop/scripts/check-bundled-backends.py \
  --arch x86_64 --dependency-lock "$LP_INTEL_BUILD/runtime-dependencies-x86_64.json"
```

完整离线渠道包还需要 Suite 中 `channel_runtime.ARCHIVES['x86_64']` 指定的官方 Node 归档，将它作为 `prepare-bundled-backends.py --channel-runtime` 的输入。省略它的构建不能记为完整离线渠道安装验收。

```sh
cd desktop
npm ci
LP_GUI_DEPENDENCY_LOCK="$LP_INTEL_BUILD/runtime-dependencies-x86_64.json" \
  LP_GUI_USE_INSTALLED_DEPS=1 \
  LP_GUI_TEST_CONFIG=src-tauri/tauri.test.conf.json \
  scripts/build-macos.sh
```

构建脚本仍使用现有共享构建锁、单 worker、签名和归档流程。通过 `scripts/install-local-app.py --test-app` 生成并复核安装计划，再按[测试安装与回滚文档](../../../docs/development/MAC_PORTABILITY_20261114.md)执行。保留日常 `io.localpilot.desktop`，隔离测试只用 `io.localpilot.desktop.test`。完成 APP 构建不能替代首次设置、真实任务、升级失败回滚及系统权限验收。

## 本轮验证

运行目录：`validation/intel-20261116/desktop`，原始输出由本轮工作环境保存。没有覆盖历史证据。

| 检查 | 结果与范围 |
| --- | --- |
| 前端 Vitest | 72 PASS，包括新增本机端点静态呈现检查 |
| TypeScript / Vite | PASS；只说明源码类型与生产构建，不证明原生连接成功 |
| 资源获取与生成器测试 | 9 PASS：ABI、系统版本、官方 wheel 选择、哈希、锁、源码记录、静态 OpenSSL 许可证与 wheel RECORD |
| PyPI 固定版本材料获取 | 35 份实际文件哈希 PASS；33 wheel 的元数据与 ABI / 平台 PASS；2 项固定源码需原生构建 |
| Playwright | 最终收集 38 项，其中新增 4 项覆盖 Intel 首次配置、显式重启、pending 恢复、模型库和协作刷新；浏览器执行受当前容器限制，见下文 |
| 新 Intel UI 夹具额外 TypeScript 检查 | PASS；首次检查命令错误要求未安装的 Node 类型，去除无关类型要求后通过，原日志保留 |
| Rust / Swift / APP / Intel 真机 | NOT_RUN：当前 Linux 环境没有 Cargo、Rust、Swift、Xcode、签名工具和 Intel macOS 设备 |

Playwright 首次运行在启动 Chromium 前失败：仓库指定的 Chromium 1248 不存在。正规安装命令尝试的官方 CDN 文件均不是有效 ZIP；随后使用现有系统 Chromium 运行，同样在启动时被容器拒绝 Unix socket（`Operation not permitted`）。两次失败及安装日志均保留，没有把它们改记为通过，也没有跳过测试断言。新增用例使用真实 React 组件和合成原生桥；即使在 Mac 上通过，仍不能代替真实模型、原生窗口或 Intel 推理验收。

## 本机 Work 必须补的最小验收

1. 在 Intel macOS 15+ 原生构建两项固定源码依赖，核验 35 个依赖和四个组件，生成目标锁与资源，跑资源真实导入及 Rust / Swift / APP 构建。
2. `npm test`、`npm run build`、`npm run test:ui`；用独立 Test APP 首次设置连接真实 CPU 端点，填写真实模型 ID 和上下文窗口，确认不会下载 MLX。模型列表读取与真正完成含工具调用任务分开记录。
3. 保存本机端点后检查 Companion 配置与电源策略；确认活动任务/未解决批准阻止激活，任务静止后显式激活，旧 Session / 收据保留，模型选择器和协作选项刷新。
4. 真实测试启动/退出/重开、取消与恢复、SSE 409、测试 APP 安装升级及故障回滚；单独记录系统权限、Intel 性能及内存。不要把 Apple Silicon 的历史结果复制为 Intel 结果。
