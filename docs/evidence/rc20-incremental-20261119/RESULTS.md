## 2. 本轮实现

活动任务的消息、工具记录和父子收据在实际可变容器上跟踪变化，将新增块和小型清单提交到现有 SQLite 存储。没有先复制/序列化整个历史，再把结果切成小块。检查点、块、意图、收据与 journal 保留原有事务边界；恢复时校验块并重建原快照，再走既有恢复规则。退役执行段与会话清理对应缓存。

正常停止服务会在 worker 静止后整理为旧版可读的 schema 3；Suite 计划记录观测到的兼容状态，在实际执行、替换 Core/APP 之前进行兼容整理。损坏块、未退出的 owner 或未知格式会阻止换包。整理按会话处理，追加 `legacy_materialized` journal，不重写此前 journal、不恢复过期备份、不丢升级后的新任务。

这解决的是频繁保存越来越长的活动任务时，反复编码全部历史的成本。**最终完整任务捕获、归档、冷恢复和旧格式整理仍有一次与记录大小有关的成本，运行时原文内存也没有变成硬上限。** 不把该改动描述成所有操作恒定时间或完整内存问题已经解决。

Core r3/r4 覆盖相同的 1,742 项，包含 RC19 全部测试和 7 项新增测试；136 个实际加载产品模块均来自冻结候选，830 个源码文件测试前后散列相同。Companion 在同环境预检了导入路径，830 个源码文件前后散列一致；未声称监测到全量测试进程的全部模块。不能从不同运行中挑出各自通过项，合并为一次“全绿”。

最后两项错误具体是：

- `HTTPTests.test_json_sse_session_and_protocol_headers`：在 `setUp()` 发现插件时，父进程等待 worker 的完整目录帧超时。该阶段包含 worker 启动、导入、回环 HTTP 初始化与目录返回，SSE/协议头断言尚未执行；原始日志不能定位哪个阶段变慢。
- `HTTPTests.test_oversized_http_is_contained`：普通参数在实际派发前进入独立 Schema 校验进程，报预算或可用性错误，尚未处理 2 MiB 响应。该统一错误文本也涵盖非超时异常，不能声称一定是超时。

两项在完全相同源码的 r3 都通过；r3 出错的两项在 r4 通过，另有定向通过记录。**这不足以确认失败仅来自环境，也不足以关闭全量门禁。** 不提高超时/内存预算，不再重复全量直到碰巧通过。后续使用独立空闲主机和阶段诊断定位，具体任务见 Work 文档。

另外保留三个事实：最初 Core/Suite 运行被中断且无完成尾部，不能推算通过；Suite r2 误载入旧 editable 源码，2 FAIL/7 ERROR/1 SKIP 记为无效混合来源试验，修正导入后才得到最终结果；各轮还有独立的定时器持久化异常堆栈，RC19 已出现，不算第三项 unittest 错误，也不能当作两项 HTTP 错误的原因。

全量结束后的具体诊断又确认两处问题。测试夹具在 `setUp()` 发现插件失败时不会执行 `tearDown()`；test-only 提交 `2e7d2e6` 改为随资源创建注册清理，原 HTTP 模块 4/4 通过，并实际注入初始化失败确认服务器、socket 和目录释放。此后没有重跑 RC20 全量，不能抵消此前全量失败。

另用真实 Timer/TaskService/SQLite 复现：回调已等待服务锁时执行正常 `suspend()`，关闭连接且 `store.failed` 为 false；随后回调改变内存状态并抛 `PersistenceError`，持久审批、检查点和 journal 保持原样、写工具未派发。该产品缺陷属于 RC20 已知未修复项，后续候选修复和验证单独记录；不把它猜成插件 HTTP 失败原因。
