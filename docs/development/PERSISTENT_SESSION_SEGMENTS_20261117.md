# 长期会话分段与恢复 — 2026-11-17

源码候选：Desktop **5.0.1-rc.16**、Core **5.0.0b33**、Suite **0.2.0b33**、Companion **0.5.7b10**；Channels 保持 **0.1.0a4**。这是 PR #15 的后续源码候选，不是新的正式 Release。RC15 及此前四类各十项审计保留各自原证据，本轮不重新计数。

## 为什么还需要处理底层记录

RC15 已把实际模型请求窗口与原始执行记录分开。模型窗口可以压缩，但 `AgentSession.messages`、工具收据、完成调用索引和历史子任务仍跨 turn 追加。每个持久边界都重新序列化这些记录，恢复时也重新构造旧 Runtime 树。只减少发送给模型的 token，不能消除这部分内存和写入成本。

另一些字段已有边界：`_usage` 每轮重置，事件流默认保留最多 2,000 条，Gateway 审计最多 1,000 条，目标板最多 100 条。本次不为这些字段重复添加清理逻辑。

## 同一个会话，多个原始执行段

已启用 SQLite 的 V5 会话，在下一任务开始前检查刚结束的任务。活动 Runtime 的序列化大小达到默认 **2 MiB** 时，服务把完整原始 Runtime 快照写入 `runtime_segments`，同时提交裁剪后的活动检查点和旧任务归档。三个写入属于同一个 SQLite 事务。

轮换保留同一 `session_id`、递增的 `turn_id`、配置和权限身份，以及最近完整 turn 的消息、工具收据、完成调用和子任务。全部目标记录、工作状态和最近轮的 finalization 账本保持原样。当前任务仍由同一个 `AgentSession` 运行；归档读取不会重新创建 Runtime 或重放工具。

旧 `TaskRecord` 的输出、收据、事件和幂等键保持原样，沿用既有 `archived_tasks` 查询。调用旧任务 ID、SSE 游标或幂等键仍返回旧结果。TaskRecord 的历史索引不被改写，Session 单独记录当前轮起点，保证轮换提交后、新任务创建前中断也能继续恢复。

2 MiB 是任务之间的触发阈值，**不是活动检查点或整个数据库的硬上限**。正在执行的单个任务不会被截断；最近完整 turn、受保护状态和当前模型窗口都可能较大。原始归档继续占用磁盘，SQLite 数据库不会凭空缩小。这里解决的是活动 Runtime、重复序列化及恢复对象持续累加的问题，不宣称无限磁盘或恒定启动时间。

## 模型前缀、权限和未完成工作

轮换不重新概括 `RequestHistory.messages`。它保留上次实际获准请求的原文和 scope，仅把 canonical 游标减去实际移走的消息数；下一轮仍在该已准入前缀后追加新输入。真正的模型压缩仍由上下文预算触发，原任务和未完成目标仍来自主机结构化状态。

最近完整 turn 的收据必须保留：下一任务的 `task.created` 检查点可能先于 `run_turn()` 重置上一轮交付状态。提前清空收据会使重启时的 finalization 哈希不匹配。此次轮换避免这个错误窗口。

产品默认非 Computer 路由使用 HybridController，即使选择 cloud-only 或 local-only。本次支持这些默认路径及 Cooperative 路由，保留当前轮用量、路由状态和出站判断；旧审计原文进入归档。某轮在首次模型派发前结束时，保留最后一个模型调用身份，避免下一轮重新从零编号。

有明确待批准请求、正在执行的子任务、未解决意图或未知副作用时不轮换。Computer 的跨轮观察/操作账本、Adaptive 路由和带精确云端授权 grants 的历史暂沿用原有方式；本次没有修改这些授权语义。普通 Full 权限任务也继续经过既有 Gateway 和操作系统边界，应用内无需重复确认不等于可以替代 macOS 原生权限。

这一步没有新增 Core 模型可调用的通用原始历史搜索工具。Companion 已有的 SQLite/FTS 对话检索继续使用，Core 旧任务结果可由现有任务 API 精确读取。不能把分段存储当成已经完成任意跨话题记忆或原文检索。

## SQLite schema 3 与回滚

schema 1 或 2 升级前，Store 使用 SQLite backup API 创建同目录、唯一命名的私有备份，并验证完整性及旧 schema 版本。备份权限为 `0600`。新表和 schema 版本在事务内提交；再次启动已升级数据库不会再生成一份同名或重复升级备份。

旧 Core b32 的 schema 2 读取器会拒绝 schema 3。降级需要先停止服务，再用升级前的完整数据库备份恢复；备份之后的新任务不在旧数据库中。不能只改 `PRAGMA user_version`，也不能用 RC14 的包管理器回滚记录替代 RC16 的数据库验收。

活动检查点启动校验仍核对 payload SHA、journal 连续性、最新 SHA 和孤立 journal。连续性改为 SQL 聚合验证：主键唯一、整数修订号、数量、最小和最大修订，以及最新校验值共同约束，避免把一生的修订号装进 Python 列表。归档段按需读取并校验 SHA；启动不反序列化所有旧 Runtime 段。

## Companion 恢复

接受云端任务的日志与会话映射之间发生中断时，恢复路径此前漏掉 `provider_kind`。重启后这条云端对话会被当成本地，下一次提交报 provider 冲突。恢复现在使用已持久化的提供方字段，保留原任务和提交 ID；旧数据仍使用既有 local 默认值。它不重放已接受任务，也不把不同云端问题合并成一个执行会话。

### 委派任务列表

原 `ui_snapshot` 把全部保留任务同时放进 `runtime.escalation_tasks` 和 `escalation.tasks`。客户端单个响应上限是 2 MiB，历史增长到一定数量后连主界面刷新都会被拒绝。

`escalation_status` 现在按 timestamp/ID 游标分页，默认 30 条、最大 50 条。列表只提供有界任务预览、总数和下一页游标；完整原始记录、请求及恢复日志不删除。`task_status` 仍按原 ID 精确查询详情。原两个 snapshot 字段继续存在，复用一次分页计算，保留现有客户端字段合同。

菜单栏委派页面提供“较早任务”和“最新任务”，刷新保留当前页；CLI 的 `escalation-status` 同样支持 limit/before。状态和取消路径去掉 `receive_task_update` 后的重复写回，普通状态更新从 5 次全图读取、2 次写回减少到 3 次读取、1 次写回。

`localpilot_tasks` 的底层存储仍是完整 JSON 映射，精确查询仍需读它。本轮解决响应溢出和重复 I/O，没有把这份历史转换成逐任务 SQLite 表；不能据分页宣称十万条任务查询已经是恒定成本。Swift 按现有界面实现修改，但本环境不能完成 macOS 原生点击验收。

## 验证与平台边界

本轮源码测试、存储对照、真实模型调用和界面环境复查分别记录，不能相互替代。当前工作环境是 Linux x86_64。浏览器页面测试仍受到 AF_UNIX 套接字限制及跨执行环境 loopback 不通的阻碍，Linux 原生构建缺 GTK/WebKit 开发依赖；Apple Silicon 和 Intel Mac 的当前候选原生交互验收仍需要对应环境。

RC14 的 Linux 动画样本、Ubuntu arm64 安装/升级/回滚，以及 b32 的 Super Agent 工程测试继续属于各自版本。RC16 仍为 `NOT_RELEASE_READY`，本次不以源码或脚本测试宣称当前候选已达到所有平台的 24 Hz 可见动画门禁。
