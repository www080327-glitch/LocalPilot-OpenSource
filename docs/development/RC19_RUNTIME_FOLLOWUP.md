# RC19 运行时续验与仍未完成的存储工作

本次在 `fe9765c` 的源码上继续处理。以下工程测试使用脚本模型、真实文件、现有 Gateway、TaskService 和 SQLite；没有调用付费模型，也不等于真实模型能力或物理桌面验收。Core 候选为 5.0.0b36。

## 已修复和补齐

### 显式选择新模型时，旧 CLI 不再提前拒绝

旧 `configure_workers()` 无条件使用只接受两个旧模型名的 OpenAI Worker 适配器，导致显式配置 `gpt-6.1-sol`、`gpt-6.2-sol` 等模型时，在请求 API 前就报模型不支持。现在保留两个旧名称的默认路径；其他显式配置的名称使用仓库已有 Responses 适配器，并继续执行当前数据政策。

真实本地 TLS 测试检查了 `/v1/responses`、完整模型名、medium、输出预算及 `store=false`。这只证明请求构造和策略正确，不证明某个账户能使用该模型。没有替用户更换默认模型，也没有标记 API 访问已验证。

### 同一会话可找回归档中的原始对话文字

开启持久化的 V5 主会话增加 `recall_history`：用大小写敏感的原文片段搜索，每次最多十项；用返回的引用和偏移读取，每次最多 4,000 个字符。引用包含归档代次、消息位置和可见文字散列。内容来自原始用户输入或助手可见回答，不是重新概括的摘要。

它不搜索系统消息、工具原始输出、隐藏推理、原生重放状态或其他会话。原始工具收据继续保留在完整归档及原有任务接口中；文档、插件等数据仍须通过各自的授权入口读取。检索结果只说明过去说过什么，不能作为文件或界面的当前观察，也不能授权执行操作。

每次访问仍经过当前读权限和文件夹授权检查，已撤销的文件夹授权不能通过历史检索绕过。归档还要求当前主机配置散列相同；改变模型、模式或预算后，旧配置下的归档可能不再适用，原始数据没有删除。这里没有宣称完成了任意跨配置记忆。

普通云端 Hybrid 路径只返回可发送的用户原文，并在限制为十项之前过滤助手文字，避免较新的助手复述挤掉用户最初的约定。其他策略仍沿用既有云端投影。不能把这个工具列入“所有结果均可公开”的名单。当前主机允许完整上下文的 Desktop 路径以及本地路径可以读取助手可见回答。

独立复核发现并修复了两个集成问题：文件夹绑定的会话切换模式会重建 Registry，导致检索工具消失；普通云端 Hybrid 会把检索结果当作未知扩展而全部遮挡。真实 V5 模式切换测试还暴露了旧代码在半完成的文件夹配置上提前刷新稳定提示的问题，已移除那次多余刷新，保留配置完成后的统一刷新。

### 已完成的更多会话可以归档

Adaptive 路由现在把旧轮次的决策和费用预留移入完整归档，只保留当前轮仍在使用的记录。当前轮费用、模型锁及恢复状态保持不变；事务失败时恢复原内存状态。

有精确云请求授权的普通 Hybrid 会话也可以轮换，但原授权散列集合保持原样，不借归档扩大授权。这个集合的长期增长尚未另行分块。

Computer 会话只有在上一轮结束、执行已静止、没有未决操作或交接义务、没有暂停或原生 UNKNOWN 日志时才能轮换。活动观察、修订号和工作状态保持不变。重启仍清除旧观察并要求重新观察，不把旧屏幕坐标或授权当作新依据。测试使用真正的 NativeComputerRuntime 和原生日志，最底层为脚本传输器；它不是 macOS 实机操作证明。

## 保持 RC18 数据回滚兼容

文字索引是可重新生成的附加表，数据库仍为 schema 3。旧 schema 1/2 的升级备份流程不变。已经是 schema 3 的数据库只增加表；原始检查点、归档段和旧任务不转换或删除。旧 Core 写入的归档缺少索引时，候选版本在首次查询时校验原文散列并补建，后续查询不会再次解析整份归档 JSON。

实际执行了三个独立进程阶段：候选写入四个任务（含检索工具收据）；未改动的 `fe9765c` 源码打开同一数据库、核对旧任务并再写三个任务；候选再次打开，检索升级前及降级期间的用户原文，再写第八个任务。原任务快照和各段散列保持一致，最终六个归档段，整个过程保持 schema 3，没有恢复备份或丢弃升级后的历史。这是实际旧源码的读写验证，不只是把版本号改回去。

## Luna 报错的准确归类

R10 的 Parser 子任务在 4,096 输出 token 上限处被截断，父任务随后尝试创建替代子任务，又超过原两个子任务预算。这是原始收据能确认的失败，不能用 Aggregate 子任务通过来掩盖。b35 已加入同一子任务的一次输出截断恢复：丢弃不完整工具调用、保留已有成功收据、要求更小的完整调用，不增加原预算。当前回归验证这条实现；本次没有重新运行付费 Luna 任务。

未注册 LIGHT/STRONG 后端、父 high 覆盖子 medium 等旧问题此前已修；本轮继续运行相关回归。R12 的系统代理 TLS EOF 和本机密钥少一个字符是当时环境问题，与模型能力或此次归档实现不是同一个问题。历史 R12 通过仍只属于当时版本和参数，不自动成为 RC19 的真实模型验收。

## 尚未完成：单个超长任务的增量检查点

Companion 的逐任务读取和分页，以及 Core 跨任务归档，都不能解决同一任务内部的完整检查点重复写入。目前每个持久边界仍复制活动消息、收据和任务记录，序列化成整份 JSON，再覆盖检查点。模型请求窗口已经有界，不代表这个持久化成本也有界。

本机用一个真实 TaskService 任务依次读取 96 份生成文件，脚本模型没有访问外部提供方，任务完成耗时 28.96 秒。下面是实际 `tool_receipt` 边界的单次观察值，不是重复测量后的统计保证。

| 已完成读取 | 检查点字节数 | 完整检查点耗时 |
|---|---:|---:|
| 1 | 41,074 | 3.1 毫秒 |
| 32 | 1,112,622 | 18.1 毫秒 |
| 64 | 1,899,820 | 39.1 毫秒 |
| 96 | 2,684,179 | 84.0 毫秒 |

最终任务收据另存入 TaskRecord 后，检查点达到 4,914,062 字节，`task.status` 边界耗时 153.5 毫秒。32、64、96 次读取附近，模型窗口均为 71 条消息，原始会话分别达到 67、131、195 条。完整原文和任务结果仍在，但同一超长任务的 CPU、写入量及恢复内存问题没有彻底解决。

下一项源码工作需要设计可增量提交的消息、工具收据、完成调用索引及子任务块，并在事务内提交一个有散列和顺序验证的清单；恢复时必须保持未知副作用、精确授权和幂等语义。若同时保留整份 schema 3 兼容检查点，每次完整写入的成本就仍然存在。因此真正切换持久格式时，还需扩展 Suite 的降级流程，在停止服务后把新格式完整物化成旧版本可读格式，验证所有升级后任务均保留，再切换二进制。这个问题需要源码和故障恢复验收，不是硬件或模型不可用造成的阻塞。

验收应比较 100、1,000 条同一任务收据下的边界耗时及实际写入量，注入提交前后中断、块丢失和散列不符，核对父子预算、暂停/恢复、UNKNOWN 不重放，并验证“旧版写入→新版继续→旧版继续→新版重开”完整历史不丢失。不能用提高压缩阈值、截断原始消息或只缩短模型窗口代替这一项。
